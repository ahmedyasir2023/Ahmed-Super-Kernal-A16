# Ahmed Super Kernal A16 — V7.7 Stable Memory & Thermal Investigation

This stage intentionally makes **NO kernel/Boot edits**. The owner confirmed working boot, regular reboot (without RC3), fingerprint, KernelSU Next root and DeepDoze on the installed V7.7. Experimental reboot PRs #11 and #12 were closed **without merging**.

## Evidence-based target

- Severe on-device memory PSI and `kswapd` high CPU were reported during freezes, but no causal mechanism was conclusively identified.
- Previously collected reboot diagnostic showed repeated failure to obtain AIDL `android.hardware.thermal.IThermal/default`, with `ctl.interface_start` failure (0x20).
- The owner's 2026-11-02 Evolution X vendor archive `Desktop.zip` contains **both** the matching VINTF fragment `etc/vintf/manifest/android.hardware.thermal-service.realme_sm7125.xml` and the init service `etc/init/android.hardware.thermal-service.realme_sm7125.rc`. The latter declares the executable `/vendor/bin/hw/android.hardware.thermal-service.realme_sm7125` and a boot dependency `/sys/kernel/boot_adsp/boot`. The archive contains only extracted vendor files, **not the executable**. Inspect existence and service runtime on device before claiming a missing HAL or blaming the kernel.
- The same vendor snapshot `etc/init/hw/init.qcom.rc` tries `memory.swappiness=140` for background memcg. The pinned Realme `mm/memcontrol.c` rejects values >100. The device's effective state must be measured; this write alone does **not** explain observed stalls.

## New read-only probe

`scripts/v7/AY_V77_Stability_Probe.sh`: one explicit run captures three snapshots at nominal 0/5/10-second intervals in `/sdcard/Download/AY_V77_Stability_Report.txt`.

It reads:
- PSI `some`/`full` cumulative microseconds, `avg10`, memory free/available and zone buddy stats.
- `kswapd` scanned/stolen pages, direct reclaim, swap-in/out, ZRAM status and the current `kswapd` kernel threads' CPU tick totals.
- Vendor Thermal HAL init service, VINTF, binary presence, ADSP dependency, selected init/logcat/SELinux denial evidence.
- Effective swappiness (including background cgroup), `kswapd_threads`, page-cluster, LMKD properties.

It does **not** modify a system property, swap, CPU governor, frequency, thermal throttling, LMKD, kernel module, or DT2W. No daemon, flash ZIP, service restart or reboot.

Copy the shell script to the Android Download folder and run with Termux:

```sh
su -c 'sh /sdcard/Download/AY_V77_Stability_Probe.sh'
```

Share the output TXT after checking for sensitive information in filtered Android logs. Prefer collecting during an actual period of stuttering.

`scripts/v7/AY_V77_Stability_Analyzer.py`: optional offline Python analyzer:

```sh
python3 scripts/v7/AY_V77_Stability_Analyzer.py AY_V77_Stability_Report.txt --json
```

Handles absent/reset counters without fabricating results. Computes PSI `total` delta/observed seconds and `pgsteal_kswapd / pgscan_kswapd`; reports `kswapd` CPU **ticks**, not made-up CPU %.

## Decision gate

1. Resolve whether Thermal HAL is absent, blocked, crashing, stuck waiting for ADSP, or not registered. Do not disable thermal protection.
2. Assess whether memory stalls coincide with failed reclaim, swap churn, direct reclaim or LMKD behavior.
3. Select **one reversible change** supported by measured data. Preserve proven V7.7 normal reboot, fingerprint, root, DT2W and DeepDoze 600s.

Oplus multi-kswapd has **two 100%-busy workers**; repeated `balance_pgdat()` calls without allocator waiters and a stale `balanced_exits` counter are consistent with a reclaim/kswapd sleep/wakeup loop. This is a credible kernel-level hypothesis, **not a proven root cause**: the observations do not show individual per-CPU watermarks or prove why `prepare_kswapd_sleep()` declines sleep.

## Safe next experiment (requires explicit on-device execution)

The existing V7.7 kernel already has a **root-only, volatile** `ay_reclaim_progress` boolean default 0; 1 selects the V7.5 reclaim-until-watermark policy while preserving freezer and stop logic. Changing it requires no flash or reboot and automatically reverts to 0 on future kernel boots.

`scripts/v7/AY_V77_Reclaim_AB_Test.sh` is an optional **20-second A/B test**, not a permanent tuning action:
- Fail closed unless root, matching sysfs parameter, baseline `reclaim_progress_enabled=0`, both thermal services running, readable PSI and battery temp not over 42°C.
- Capture 10 seconds baseline with `reclaim_progress_enabled=0`, then 10 seconds opt-in with `reclaim_progress_enabled=1`.
- Automatically restore mode 0 using a shell exit/signal trap and verify `/proc/ay_reclaim_status` shows the original mode.
- **SIGKILL, power loss or a userspace crash cannot invoke a shell trap**; the parameter may remain enabled until explicitly restored or rebooted. Therefore run only while the screen is on, with the device responsive, and inspect the result before deciding whether to recommend this mode.
- The test alters only that single kernel sysfs parameter; no write to swap, CPU, governor, thermal, KernelSU, VINTF, Android init, or any partition.

Run after reviewing the risk, from Termux:

```sh
su -c 'sh /sdcard/Download/AY_V77_Reclaim_AB_Test.sh'
```

Output: `/sdcard/Download/AY_V77_Reclaim_AB_Result.txt`; compare per-interval PSI *total delta* (not only avg10), kswapd CPU tick deltas and reclaim efficiency. If there is no improvement or stalls worsen, leave the default mode 0. Do not auto-enable after reboot or publish a new kernel before a controlled result.

### Interpretation correction: `kswapd_waiters` is not a global allocator count

The Realme source increments `kswapd_waiters` **only** in `allow_direct_reclaim()` when low pfmemalloc reserves cause a direct-reclaim caller to be throttled (see `mm/vmscan.c`, near `throttle_direct_reclaim`). It does not track ordinary user-space allocations. Therefore, `balance_zero_waiters` near 100% **cannot by itself prove** kswapd work is unnecessary or that its loop is broken. It establishes only that the vendor early-exit condition often sees no such special throttled waiters. Underlying memory zone high-watermark, per-CPU draining, and per-node reclaim interaction still require evidence.

The decisive measurable problem is two kswapd workers at about one full core each alongside 78.34% memory PSI full, **after root modules were disabled and Thermal HAL was restored**. The A/B test must compare cumulative PSI and kswapd tick deltas, not only total memory used or the count of `balance_zero_waiters`. A single 10-second test is not a definitive performance benchmark.


## CI-completed A/B decision tool (2026-11-05)

`scripts/v7/AY_V77_Reclaim_AB_Analyzer.py` parses only a *complete* `AY_V77_Reclaim_AB_Result.txt` from the short on-device controlled test. It requires:

- Baseline START/END `mode=0` and experiment START/END `mode=1`, in order; strictly increasing times between each pair.
- Corresponding `reclaim_progress_enabled` readbacks and explicit `RESTORED reclaim_progress_enabled=0` proof from the shell exit trap.
- Nondecreasing PSI cumulative microseconds, `kswapd` CPU ticks for the **same process IDs**, and consistent VM counters.
- A comparison of **PSI full stall percentage computed from cumulative totals** and **kswapd CPU ticks/second**. It records reclaim efficiency and swapping/refault rates as supporting indicators.

The result deliberately labels any apparent improvement only `PROMISING_SHORT_SAMPLE_ONLY`; it **does not** authorize automatic permanent tuning. When the restore confirmation is missing, it emits `NO_RESTORE_CONFIRMATION` and warns to inspect the current kernel mode before any further testing. Host CPU USER_HZ is not assumed.

Run offline:

```sh
python3 scripts/v7/AY_V77_Reclaim_AB_Analyzer.py AY_V77_Reclaim_AB_Result.txt
```

CI includes seven additional tests of mode mismatch, incomplete or duplicated intervals, missing restoration, regressed stalls, counter resets and changing worker ticks, alongside the six stability analyzer tests.

**Decision gate remains unchanged:** no kernel patch, no default mode flip, no change to kswapd worker count, no flash ZIP, no memory or thermal governor changes until the *real on-device A/B report* arrives and is independently checked. The two prior reports show severe load; they do not contain this A/B result.
