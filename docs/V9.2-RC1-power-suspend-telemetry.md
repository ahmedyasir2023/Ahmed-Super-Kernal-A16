# V9.2 RC1 — Power & Suspend Intelligence

**Target:** Realme 7 Pro RMX2170, Evolution X Android 16, Linux 4.14.336.  
**Base:** V9.1 Bounded Reclaim source branch.  
**Status:** Diagnostic-first experimental development; not a stable release and not a flashable package.

## Scope of V9.2 RC1

V9.2 RC1 adds passive PM suspend-cycle observability to the existing cpu-boost.c driver and a read-only device snapshot script.

The kernel observer records:

- PM_SUSPEND_PREPARE event count.
- Paired PM_POST_SUSPEND event count.
- Unmatched post events.
- Whether a PM cycle is currently pending.
- Last, maximum and cumulative CLOCK_BOOTTIME elapsed time between PREPARE and POST.

The read-only endpoint is:

    /proc/ay_power_suspend_status

The device probe is:

    scripts/v9/ay_v92_power_suspend_probe.sh

## Measurement semantics — do not conflate these signals

1. **DeepDoze CPUFreq cap:** confirms that the existing 600-second screen-off policy has activated and constrains CPUFreq policy ceilings. It does not prove system suspend.
2. **PM notifier elapsed time:** PREPARE-to-POST CLOCK_BOOTTIME includes time spent suspended, but also includes PM preparation and resume overhead. It is not a precise hardware suspend-residency counter and does not classify success.
3. **suspend_stats:** use the kernel's success/failure counters and failure reasons to identify actual suspend outcomes.
4. **CPUIdle state*/time and state*/usage:** per-CPU idle-state residency and entry counts. These are not the same as system suspend residency.
5. **wakeup_sources:** accumulated wake-source accounting. Compare two snapshots from the same boot to identify increasing event counts and active/prevent-suspend time.
6. **Battery current/capacity:** instantaneous/contextual readings only. They are not a controlled battery-drain measurement.

## Safety contract

- No changes to suspend entry/exit policy or platform suspend code.
- No new timer, delayed work, polling loop, workqueue, wake lock, wakeup event or service.
- No CPUFreq governor, minimum/maximum frequency, boost percentage or boost-duration changes.
- Existing 600-second DeepDoze timer and immediate wake restoration remain unchanged.
- No changes to DT2W/touchscreen, fingerprint, thermal HAL/limits, SELinux, KernelSU Next, SUSFS, ZRAM, DTB or vendor device drivers.
- /proc/ay_power_suspend_status is read-only (0444).
- The probe reads existing interfaces only. It does not mount debugfs or write sysfs/procfs controls.

CI must run the existing V9.1, V8.1 and V7 DeepDoze source-contract validators, then the V9.2 observer validator, and compile the pinned ARM64 source with the existing pinned Clang 21 toolchain.

The generated Image.gz is a non-flashable CI artifact. A successful compile is not a physical boot test and does not authorize replacing a known-good Boot image.

## First device capture and matched A/B

Use the same probe for the currently installed V9.1 baseline and later for V9.2. On V9.1, the new PM notifier endpoint is expected to be unavailable; the existing suspend_stats, wakeup_sources, CPUIdle, DeepDoze, CPUFreq and battery interfaces are still captured.

For each kernel version:

1. Reboot once and allow the ROM to settle.
2. While the screen is ON, capture a baseline snapshot:

    su -c 'sh /sdcard/Download/ay_v92_power_suspend_probe.sh' > /sdcard/Download/AY_V91_before_idle.txt

3. Use the phone normally, then leave it screen-off for at least 30 minutes; a longer overnight interval is useful for battery-drain evaluation. Do not run the probe while the display is off.
4. Wake the phone and capture the second snapshot:

    su -c 'sh /sdcard/Download/ay_v92_power_suspend_probe.sh' > /sdcard/Download/AY_V91_after_idle.txt

5. Repeat the same two-snapshot sequence on V9.2, changing the filenames to AY_V92_before_idle.txt and AY_V92_after_idle.txt.
6. Preserve all four reports. Do not reset counters or change governor, CPUFreq limits, DeepDoze parameters, wake sources, thermal settings or memory sysctls during a capture.
7. Compare counter deltas, not raw totals: suspend_stats success/fail, wakeup-source event/time fields, CPUIdle state usage/time, PM notifier events on V9.2, and battery charge/capacity where exposed.

Keep ROM build, SIM/Wi-Fi state, brightness, screen-off duration, battery range and background workload matched. The report is a set of signals, not one score. A DeepDoze entry without corresponding improvement in suspend/idle residency is not evidence of low screen-off power.

## RC1 acceptance gates

- Kernel build and all static source contracts pass.
- /proc/ay_power_suspend_status exists and is readable.
- PREPARE/POST counters pair consistently during normal suspend cycles.
- suspend_stats and wakeup-source accounting remain available and coherent.
- CPUIdle residency can be captured where the platform exposes it.
- Fingerprint, physical DT2W, normal restart, thermal behavior and KernelSU/SUSFS runtime remain intact.
- No regression in screen-on wake response or foreground navigation.
- Battery and suspend improvements are claimed only after matched on-device measurements.

**No battery-saving or performance improvement is claimed by the telemetry-only RC1 source change.**
