# V7.7 RC3 — Normal reboot PMIC reset fix (hardware unverified)

## User symptom
RMX2170 (Evolution X Android 16, Nov 2 2026) boots V7.7 with functioning fingerprint and KernelSU root, but ordinary **Restart** appears to turn the phone fully off. A simultaneous hardware-key Fastboot entry allows booting System or OrangeFox. The user-provided 2026-11-04 diagnostics show `ro.boot.bootreason=reboot,`; pstore was empty, so the prior failed reset sequence could not be inspected. Qualcomm watchdog ping logs are not proof of a bite; the repeatedly unavailable Thermal HAL service is a separate ROM/vendor concern.

## Source-level cause hypothesis
Original Realme Linux 4.14 `msm_restart_prepare` chooses `PON_POWER_OFF_HARD_RESET` for an ordinary no-target reboot on this device-tree configuration. The PMIC/firmware may leave the device powered off instead of automatically restarting. This is a hypothesis, not hardware-verified.

Android init uses Linux RESTART2 with a reboot target; its normal target is ordinarily an empty string (sometimes a named normal/reboot reason). RC3 matches only those plain normal restart reasons, not recovery/bootloader/EDL/shutdown. It changes only this late shutdown/reset path.

## Behaviour
- `ay_normal_warm_reset_probe=1` **by default each boot**; normal reboot uses `PON_POWER_OFF_WARM_RESET`.
- Can be disabled by root (mode 0600); no daemon and no persistence requirement. Expected parameter path: `/sys/module/msm_poweroff/parameters/ay_normal_warm_reset_probe`; actual sysfs name/path requires checking after boot.
- Other reboot reasons including `recovery`, `bootloader`, `edl`, `fastboot`, `android`, panic and actual `poweroff` still use unchanged OEM paths.
- No other Qualcomm PMIC operations, PS_HOLD, watchdog, frequencies, DeepDoze, touch/DT2W, fingerprint, KernelSU Next or SUSFS modifications.
- Reboot is an infrequent event; changing normal-restart selection does not introduce background CPU work or screen-off polling.

## CI / release gates
- RC2 ARM64 built successfully in Actions 41910754038.
- RC3 must compile with strict vendor-driver/DTB change allowlist and the V7.2 unchanged screen-off SHA-256 contract.
- A flashable **candidate** must match a **known, independent** installed Boot SHA-256 before any writes and provide a verified reversible Boot image. No blind writes or random AVB bypasses.
- User must separately back up the *actual current* Boot in OrangeFox. No guarantee of success until at least one supervised reboot using RC3 succeeds.
